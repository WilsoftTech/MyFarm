## Scope and reuse

The owner approved farmer-confirmed assisted registration and the visit privacy policy during continuation on 2026-11-21 (D-P14-004/005). An officer may prepare details, but the farmer's own existing login must explicitly accept the exact review before registration records or assignments are created. Optional GPS, private photos under existing limits, current assignment checks and recovery of refused local drafts remain mandatory.

`src/modules/extension-officers/contracts/work.ts` reuses the existing farmer profile and farm schemas, UUID validation, calendar rules and coordinate validation. It defines proposals with a named target account, separate exact version/hash/boolean confirmation, planned/completed visits, optional paired coordinate strings, optional explicit follow-up and problem facts, versioned completion commands and bounded photo metadata. Credential, actor, role, tenant and object-path claims are rejected. No diagnosis or default agronomic recommendation is generated.

The offline envelope requires a stable matching clientMutationId/requestId, device identity, schema/local versions, valid local timestamps and pending/sending status. Client clock corrections are allowed; local timestamps neither authorize writes nor order server effects. Each operation has a strict payload; unrelated financial operations and forged actors are rejected. This is a transport contract, not an implemented queue or sync endpoint.

`domain/registration.ts` accepts trusted current account/draft facts and an explicit trusted server clock. Only the named active target can confirm. Missing/ambiguous consent, discarded drafts, changed versions/hashes and exact expiry reject. A matching completed review is identified as a replay even after expiry; persistence must still recheck current access before returning a receipt. The function creates no farmer, farm, grant or credentials. It deliberately has no default review duration while D-P14-006 is pending.

No new dependency, database table, migration, storage privilege, API, UI or IndexedDB version is introduced by T004. Existing T002 dashboard persistence is separate. The minimal persistence work prepared during review remains in ignored local preparation, not enabled application code. No hosted or production change was performed.
