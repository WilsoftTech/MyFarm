Enforces the replay contract: push and photo upload now read the receipts already held on a key and refuse it when another operation used it. PostgreSQL tests then prove the replay behavior T005 and T008 relied on, confirming D-P07-007's choice not to add a `MutationReceipt` table.

PASS on real PostgreSQL: the source's critical test, where a lost acknowledgement followed by five racing retries leaves one transaction; five racing first attempts; racing retries of tasks and done records; a retry 30 days old, far beyond the 14-day limit, still replays; a changed payload is rejected and the original stands; a key reused on another operation is rejected with no second effect, including for photos; two devices finishing one activity, where one wins, the other gets a conflict with the current record and nothing is overwritten; two devices recording separate expenses keep both; a member revoked while offline is denied with no effect and the same entry goes through if access returns; pull pagination visits every row exactly once; an expired cursor partway through tells the phone to restart.

**Known limit:** the check that refuses a reused key reads before writing, so a faulty client racing itself across two different operations could slip past it. Each operation's own receipt still stops any repeat of that operation. Normal clients never reuse a key.
