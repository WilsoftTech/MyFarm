## Delivered behavior and reuse

The `extension-officers` application services derive the actor from the verified current session and scope. The repository rechecks current active accounts, AGENT membership, explicit assignments, current farm ownership, active owner FarmMember and FARMER membership. Dashboard reads run in one repeatable-read transaction, with a database clock and bounded source facts; incomplete inputs yield unavailable totals. Farm labels paginate separately, using an anchor from the permitted assignment set. Visits/follow-ups/problems are read under the assigned officer and matching parent references, selecting only count-relevant columns rather than observations, recommendations or GPS.

Owner grant/revoke transactions recheck authorization around receipt waits. Concurrent identical grant requests produce one assignment and audit receipt; changed payloads under the same request conflict. A distinct duplicate active grant rolls back its receipt. Revocation increments the expected version, cannot be reversed through the runtime role, and removes the assignment from subsequent dashboard reads. Old visits are not transferred to a newly assigned officer. Permissions do not imply global search, money records, exports or farmer impersonation.

The existing `/agent?scope=...` workspace now shows My farmers, Visits today, Follow-ups and Problems using real permitted database records, including a true zero/empty state. It shows the check time and explicitly requires connecting/reloading for current access/counts. It does not claim an offline cached snapshot is live. The farmer manages named assignments at `/farms/[farmId]/officers`, linked from the farm page. Grant/revoke requires an initially unchecked consent control; input and stable request IDs survive interrupted saves, and offline submission is disabled without discarding form input. Lists are bounded and explain truncation.

Reused `AuthorizationService`, current-role policy, existing registry ownership conventions, FoundationError/HTTP boundaries, server-command feedback, audit receipt uniqueness, installed Prisma/Zod, farm calendar, Button/Input/Field primitives and `useProductionSubmit`. No dependency or lockfile change. The existing owner-only farm export includes the four new farm record types, omitting other people's account IDs and internal request hashes. Officers still cannot export a farmer's farm. The export coverage regression was fixed in the implementation, not by weakening the test.

## Schema, policies and migration

Additive migration: `20261121190000_officer_dashboard`. Four new tables: OfficerAssignment, OfficerVisit, OfficerFollowUp and OfficerProblem. Visit-related tables are R001 projection storage; their runtime mutation grants remain absent pending T004-T006. Composite assignment/visit keys bind farm, tenant and officer; validity/status/version/paired-coordinate checks reject invalid data. A partial unique index permits at most one unrevoked grant per farm/officer. No existing table data is rewritten or dropped.

`supabase/policies/extension-officers-runtime.sql` is placed before browser lockdown in the ordered manifest. New public tables have RLS enabled in the migration. Browser roles have no table/function access. The existing server-only runtime architecture retains read policies and grants only assignment creation and guarded, one-way revocation; visit/follow-up/problem writes remain denied. Owner/officer eligibility is checked in application transactions and assignment insert/update policies. Private helper functions are SECURITY INVOKER, with browser/PUBLIC execution revoked.
