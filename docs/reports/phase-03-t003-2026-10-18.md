## Reproducing the signed-in suite

Create a fresh, isolated PostgreSQL 17 database named `myfarm_phase01_test` on loopback. Set the owner connection as `TEST_DATABASE_URL`; the configuration rejects non-loopback or differently named databases. Its setup deploys migrations and the actual provider manifest, seeds synthetic identities and returns cleanup. Run database suites serially with this suite because it tests a temporary permission outage.

For the browser build, set `DATABASE_URL` and `DIRECT_URL` to that isolated owner URL, `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:3211`, and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=fixture-publishable-key`; then run `npm.cmd run build`. Run the signed-in command above with `TEST_DATABASE_URL` still set. The config starts the local Auth fixture and Next server with `myfarm_runtime`. Public provider values are compiled by Next.js, so changing only server environment values after a different build is insufficient. Restore the ordinary environment and rebuild afterward. Preserve unrelated generated-file edits across builds.

The test-only HTTP Auth fixture validates synthetic signed sessions and serves the user endpoint; application source has no test-mode authentication bypass. This proves application UI/service/database behavior with a controlled provider contract, not actual hosted Supabase Auth. No clean-clone CI substitution run is claimed.
