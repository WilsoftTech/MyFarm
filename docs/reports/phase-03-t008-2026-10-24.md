## Design notes

- **No per-batch lock.** Unlike crop cycles there is no shared capacity to serialize, so only the audit receipt's unique key serializes retries. Distinct requests create distinct batches, even with identical fields.
- **Retries.** An identical normalized retry replays the original batch. A changed field or a different farm returns 409 with no new receipt. A replay still succeeds after the enterprise closes, because it returns committed history rather than starting new production.
- **Rechecks.** Membership is rechecked before the receipt claim and again after it, so a member revoked while waiting on a concurrent receipt can neither create nor replay.
- **Current quantity** has no column. Every view derives it from the starting count with source `STARTING_QUANTITY`; Phase 5 movements will extend the derivation.
- **Defense in depth.** The database INSERT policy independently rejects forged creators, CLOSED/version-2 rows and crop enterprises, even for raw runtime-role inserts.

## P3-C1 — non-UTC database time zone (new condition, pre-existing defect)

The first integration run failed one Phase 1 test, `database.test.ts` "limits distinct private grants…": both concurrent grants were accepted. It failed in 4/4 reruns. Investigation:

- Windows and database clocks agree to about 1 ms.
- The advisory-lock SQL serializes correctly when replayed with raw `pg` clients.
- The new cluster inherited `TimeZone = Africa/Nairobi` from WSL, whereas CI's `postgres:17` image uses UTC.
- With only the disposable database set to UTC, the test passes, and the whole suite passes 101/101.

The evidence points to timestamps produced by Prisma's `@default(now())` (client-side) being interpreted in the server's session time zone, which stores them 3 hours early and puts them outside the limiter's `clock_timestamp()` window. This is consistent with every observation, but the exact parameter encoding was not traced. The defect is in Phase 1 code; T008 does not touch it and does not change it.

Hosted Supabase and CI run in UTC, so no current environment is known to be affected. Any non-UTC database would, however, mis-store Prisma-generated timestamps and weaken the private-file rate limit. Recommended follow-up, which needs owner direction: trace the encoding, then either pin the session time zone to UTC for every connection or make timestamp defaults database-generated, and add a regression test that runs under a non-UTC time zone.
