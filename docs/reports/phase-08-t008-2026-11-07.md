## Changes

`FarmProfitabilityService.trends` authorizes the farm and validates the filters before reading anything, exactly as the dashboard and metrics do. It reads every record in the chosen basis and every season's crop cycles, so each side of a trend picks its own season or batch. Figures are calculated on each request with an as-of time; nothing is stored (D-P08-008).

- **Crops need a season.** For all records or chosen dates there is no "this season" to compare, so crop trends are left out and `cropsNeedSeason` says so. Batch trends cover whole lives in every view.
- **A season opened by its ID** beyond the 100 listed still compares with the listed seasons before it.
- **Facts:** the existing metric read now also returns each crop cycle's season and each batch's animal type and acquisition date. No schema change and no new query.
- **Endpoint:** `GET /api/v1/farms/{farmId}/profitability/trends` uses the same filters, private headers and error responses as the metrics endpoint.

Reading writes nothing, so there is no audit event or replay receipt; repeating a request gives the same answer.
