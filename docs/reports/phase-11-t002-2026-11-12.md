## What T002 adds

A farmer asks a question about one farm and gets an answer worked out from that farm's records. Each step, in order:

1. **Authorize** the farm from current membership; the question can't name a farm, tenant or person.
2. **Retry check:** a retry with the same request ID returns the stored answer. It isn't counted again and the provider isn't called again.
3. **Limit:** count the question against the person's 20 a day (D-P11-004); over that, HTTP 429 and nothing is stored.
4. **Intent:** detect it. A detector that fails, stalls or adds anything to the intent leaves the question unsupported, so it can never widen the scope.
5. **Figures:** for "most money", get the figures through the farm screen's own authorized service (Phase 8), for the season or dates chosen there, and build the T001 evidence per currency.
6. **Explain** with a 20-second limit, outside any database transaction, then check the result with the T001 rules. If the provider fails, stalls, returns the wrong shape or fails a check, MyFarm's plain answer is shown and the reason is kept.
7. **Store** the question, evidence and answer for 90 days, and log the provider's calls, tokens and estimated cost per farm.

Crop or animal advice gets the extension-officer referral (D-P11-005). Any other question gets a sentence saying what can be asked. Neither calls the provider.

## Database

- **`AssistantQuestion`:** one row per question, private to the person who asked.
  - Both timestamps are set by the database. A check fixes the kept-until time at exactly 90 days after asking.
  - The app's role can add a question only for an active farmer member of the farm, asked within the last minute. It can read and delete questions but never change one.
- **`AssistantUsage`:** provider, model, calls, tokens and estimated cost per farm, with no question text, so cost stays after a question is deleted. The app's role can only add rows.

Both tables have row security on and no browser access.

**A defect found and fixed in testing.** A database check that reads a missing JSON key gets NULL, and PostgreSQL accepts NULL, so a row with no version passed. The check is now `COALESCE(..., false)`. The Phase 10 `FarmInsight_evidence_check` has the same pattern. Only the server writes there, so nothing is wrong today, but it should get the same fix in a later migration.

## Engineering readings for owner confirmation

1. **Tables.** The specification's proposal (conversation, message, knowledge document, AI usage) became two tables:
   - **One row per question.** Answers aren't a chat that builds on earlier messages, so each question stands alone and can be deleted on its own.
   - **No knowledge table,** because answers use records only (D-P11-005).
   - **Usage is its own table,** so cost outlives a deleted question.
2. **Who sees a question.** Only the person who asked, even on a farm with several members (D-P11-003).
3. **Deleting after 90 days.** An expired question is hidden at once. It is deleted when its asker next asks a question, so no unattended job runs, as D-P09-012 requires until the owner approves automation. Questions of someone who never asks again stay hidden in the table until a reviewed clean-up removes them. That clean-up is a step for the T010 audit.
4. **"A day"** means any 24 hours, the same way the other limits count.
5. **The fake recognizes words.** It knows a few money words ("most money", "profit", "margin", "earn") and advice words ("spray", "disease", "seed", "vaccine"). Real wording will be tested when a provider is chosen.

## Tests

`tests/integration/ai-assistant-service.test.ts`, 13 tests, real PostgreSQL 17 under the restricted runtime role:

- **AC001:** the source example from real records. Poultry made UGX 1,420,000 in season 2026A, with sales, costs and the runner-up. The answer is kept exactly 90 days and its cost is logged.
- **Retries:** three identical requests at once give one stored question, one count and one usage row; a reused request ID on another farm is refused.
- **No conclusion:** missing evidence gives no conclusion and makes no provider call.
- **Referral and unsupported:** an advice question gets the referral; an unsupported question gets the "what can be asked" sentence.
- **Two tenants:** another farmer can't ask about, list or delete this farm's questions, and their farm's larger figure never appears.
- **Fake scope:** a farm, tenant or actor in the question is refused; another farm's season is refused; guessed question IDs are refused.
- **Prompt injection:** a provider following an injected question is refused, whether it invents amounts in digits or words, names the wrong winner, cites another farm's figure, adds an `sql` field, sends text or nothing, or reports negative tokens.
- **Detector abuse:** a detector that adds a farm or invents an intent leaves the question unsupported.
- **Outage:** a provider error and a stalled provider (timeout) both show the plain answer, with the call still logged.
- **A good provider:** its words are used, and its tokens and cost are logged exactly.
- **Limit:** past 20 a day nothing is asked, stored or logged; another person is unaffected.
- **Retention:** expired questions are hidden and then deleted only for their asker; the farmer can delete sooner; cost stays.
- **Runtime role:** can't change a question, stretch or backdate retention, add one for a non-member, or change or delete usage; the table refuses an unversioned answer.
