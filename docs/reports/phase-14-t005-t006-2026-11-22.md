## Delivered scope and reuse

An active officer prepares a seven-day draft for a named existing account. No farmer, farm, membership or assignment exists until that farmer signs in and explicitly accepts the exact version and digest. Either participant may discard an unaccepted draft. Acceptance serializes the draft and target account, rechecks current eligibility and expiry, and atomically reuses the existing registry creation routines to create farmer, farm, owner membership, named assignment and audit receipts. Concurrent acceptance and retry return one result. Completed receipts keep the digest and resulting farm reference and remove copied profile fields. Expired drafts are removed lazily; no scheduled purge or backup-retention guarantee is implied.

Visit services validate the current officer, assignment, farm owner and related parent before reading or writing. Visits carry optional paired GPS coordinates, explicit observations and recommendations, optional follow-up and explicitly flagged problems. Recommendations are entered by the officer, not generated. Follow-up completion and problem resolution use version checks, one-way transitions and receipts. Reassignment does not transfer the previous officer's work.

Private photos use the existing two-MiB PNG/JPEG/WebP checks and session-based storage adapter in a separate `officer-visits` namespace. Reserve, upload and publish are separate stages; publish rechecks current access and writes its audit receipt atomically. A revoked upload cannot publish metadata. Signed reads require the owner or currently assigned officer. Browser table access remains denied; storage policies bind the live session, exact reserved object, tenant and parent. Hosted object storage has not been exercised by these local tests.

Offline work reuses the existing account-partitioned Dexie database, outbox, photo blobs, storage checks, sender lease, dependency ordering and sync-center recovery controls. No IndexedDB version or new dependency is added. Officer envelopes retain mutation/device IDs, timestamps and versions; the server derives authority independently. Retries use the same command ID. Denial keeps local work and photos with an explanation and recovery/download controls. The text download excludes photo bytes, as already disclosed by the sync center.

The dashboard exposes when assignments have finished saving before offline navigation. Review found that the previous account pointer could cause the new officer cache to be deleted; the authorized server view now establishes its account before caching, and sign-out generation checks still prevent restoring a signed-out account. Two component regression cases and the desktop/mobile offline journey exercise these boundaries. Test cleanup now removes its own organization audit records before deleting its synthetic organization.

## Schema, compatibility and rollout

The additive migrations `20261121190000_officer_dashboard` and `20261121233500_officer_registration_visits` create six officer tables with composite parent constraints, bounds, versions and RLS. Ordered provider files add guarded runtime writes, immutable completed consent and private storage policies. Existing registry entry points wrap the extracted transaction routines, preserving ordinary self-registration. Farm exports include the new owner-scoped records without internal actor IDs or consent hashes. Officers receive no money/export access or farmer-tenant membership.

Only isolated loopback PostgreSQL is used. Hosted migrations, provider SQL and deployment are not performed. Roll back application routes while retaining additive tables and audit history; do not drop consent records. Apply migrations and the complete ordered provider manifest only through a separately authorized hosted recovery/verification procedure. Object bytes require their own backup and recovery verification.
