## Implementation plan

**Client.** Existing pages stay private, server-rendered and `no-store`, and the service worker never stores signed-in HTML or API responses. A new static `/offline` shell reads the account's own IndexedDB database, so farm data never enters the shared HTTP cache. Navigations try the network and fall back to the shell only when it fails.

**Dependencies.** Add `dexie` as an exact version at T002. The source (P0455) and the approved technology stack name it, it is Apache-2.0, and it loads only on the offline route. Raw IndexedDB would mean hand-writing the schema upgrades and transactions that protect queued records. No service-worker library is planned: the worker is small enough to hand-write, which avoids a build plugin on Turbopack. Phase 5 found that Windows npm can leave the lockfile incomplete for Linux, so the lockfile change must pass the Linux dry-run check and hosted `npm ci`.

**Sync.** Reuse what exists before adding tables. `requestId` already gives each command a receipt in `AuditEvent` with a request hash, so it can act as `clientMutationId`, and same-key replay already returns the stored result. T011 must prove this under the batch endpoint before the proposed `MutationReceipt` table is dropped. `POST /api/v1/sync/push` will send each command through the existing services one at a time, so all current authorization, validation and atomic writes still apply.

**Pull.** The design is deliberately left for T010. The proposed change log needs a sequence that cannot skip a late commit, which the architecture document calls out as requiring proof. T010 will choose between that and paged scoped snapshots.

**Photos.** There is no Document model yet, so T004-T006 need an additive schema and use the existing private storage. Hosted storage and schema need separate authorization.

## Risks

- **Size:** this is the largest phase so far, and service-worker behavior is hard to test. Playwright can exercise offline reloads, but real low-cost Android behavior needs a real device, which this environment does not have. That measurement will stay open until someone runs it.
- **Stock:** offline entries cannot guarantee stock availability. Offline sale is not one of the eight actions and stays online-only.
- **Version skew:** a service-worker or local schema update must preserve queued entries. T003 and T012 must test upgrades with entries waiting.
- **Offline sign-in:** a browser cannot check a session while offline, so the shell relies on the last signed-in account on that phone, as approved in D-P07-003. The server still rechecks everything on sync, so a revoked member cannot commit.

## T001 scope and verification

Adds `src/modules/offline-first/domain/storage.ts`, `contracts/storage.ts` and `tests/unit/offline-storage.test.ts`. They define the approved limits, storage warnings, the mapping from browser save errors to "not saved" results, per-account database names, which stores sign-out clears, and the service-worker caching rules. No schema, route, dependency or UI change, and the application does not import the module yet.

Warnings count waiting time from the oldest unsent entry rather than the last sync, because a farmer with nothing waiting is not at risk. Durability warnings never block recording; only a full queue does. The 10-day and 400-entry warning points and the 50 MB low-storage threshold are engineering choices within the approved limits, open to owner review.
